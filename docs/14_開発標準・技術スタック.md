## 2. リポジトリの構成

```
soilflow/
├─ apps/
│  ├─ web/                     Next.js
│  │  ├─ app/(auth)/login/      SCR-01
│  │  ├─ app/reception/         SCR-10〜15
│  │  ├─ app/terminal/          SCR-20〜22
│  │  ├─ app/office/            SCR-30〜36・40〜44・50〜57・60〜62
│  │  ├─ components/            共通の部品（Button・Dialog・StatusPill・DailyGrid…）
│  │  └─ lib/api/               openapi.yaml から生成した型と呼び出し
│  └─ api/                     NestJS
│     ├─ src/modules/<名前>/    04 2.2 のモジュール（controller・service・repository・dto）
│     ├─ src/common/            Guard・例外の変換・ログ・CSRF
│     ├─ src/adapters/          freee・sendgrid・storage・kms（試験ではにせものに差し替え）
│     └─ prisma/                schema.prisma・migrations/（SQL）・seed
├─ packages/
│  ├─ billing/                 請求計算（11 計算仕様書。billing.js・billing.test.js）
│  └─ pdf/                     帳票（10 帳票設計書）
├─ infra/                      Terraform
├─ e2e/                        Playwright（試作画面のシナリオと同じ流れ）
└─ docs/                       資料
```

## 3. 名前の付け方

| 対象 | 決まり | 例 |
|---|---|---|
| DB のテーブル・列 | 英語・snake_case・複数形のテーブル（01 用語定義書の英語名） | `report_rows.vehicle_class_id` |
| API の項目 | camelCase | `vehicleClassId` |
| TypeScript の型・クラス | PascalCase | `ReportRow`、`FreeeRegistrationService` |
| 変数・関数 | camelCase。業務の言葉は 01 の英語名 | `effectiveItemId`、`billingPartyIdFor` |
| 画面の文言 | 日本語。お客さまの言葉（受入れ・納品・便・台数・印）。01 の「使わない言葉」は使わない | |
| 状態の値 | 英大文字（DB・API）、画面は日本語の表示名 | `AWAITING_SIGNATURE` →「サイン待ち」 |
| エラーコード | 英大文字・_ 区切り（08 3.2） | `TRIP_LOCKED_BY_SLIP` |
| ファイル | kebab-case（画面の部品は PascalCase） | `billing-run.service.ts`、`DailyGrid.tsx` |

## 4. コードの決まり

| No | 決まり |
|---|---|
| 1 | 金額は整数（円）。`number` で扱い、小数の計算をしない。消費税は `packages/billing` の `taxOf` だけで計算する |
| 2 | 請求の計算は `packages/billing` だけに書く。API・画面に同じ計算を書かない |
| 3 | 日付は `YYYY-MM-DD` の文字列で受け渡す。`Date` に直すのは日本時間の変換が必要な所だけ |
| 4 | 更新系は1つのトランザクションで、業務の変更と操作履歴を一緒に書く |
| 5 | 更新系は `version` を確かめる（07 8章） |
| 6 | 外部（freee・SendGrid・Storage・KMS）は adapters を通して呼ぶ。サービスから直接 HTTP を呼ばない |
| 7 | freee・メールの処理は冪等にする（09 4.4）。ID を保存してから次の手順へ |
| 8 | ログに秘密の情報・個人情報を出さない（13 6章） |
| 9 | 画面は受付・サイン端末に金額を出さない。API の応答にも含めない |
| 10 | 例外は共通の変換で 08 3.1 の形にする。DB のトリガーのエラー（`SF_…`）もここで変換する |
| 11 | 画面の文言は部品に直接書かず、画面ごとの文言のファイルにまとめる（言い回しの統一のため） |
| 12 | アクセシビリティ：ボタンには文字か `aria-label`、色だけで意味を表さない、Tab で操作できる |

## 5. Git の使い方

| 項目 | 決まり |
|---|---|
| ブランチ | `main`（いつでも検証へ出せる）、作業は `feature/<ID>-<内容>`（例：`feature/FR-RCV-07-cell-click`） |
| コミット | Conventional Commits（`feat:`・`fix:`・`docs:`・`test:`・`refactor:`・`chore:`）。本文に関係する要件の番号 |
| PR | 小さく（目安 400行以内）。説明に「何を・なぜ・どう確かめたか」と要件・画面の番号。CI が通ったものだけマージ |
| レビュー | 1名以上。セキュリティ（13）・請求計算（11）・DB の変更は特に確認 |
| リリース | `v1.0.0` のようにタグを付けると本番へ（12 8章）。変更内容を `CHANGELOG.md` に書く |
| 資料 | 仕様を変える PR は、同じ PR で docs を直す。範囲・仕様の変更は台帳に CHG 番号を取る |

## 6. 試験の決まり

| 対象 | 決まり |
|---|---|
| `packages/billing` | 正解データ（`spec/billing-golden.json`）が全部一致すること。行の網羅率 100% |
| API のサービス | 主な分岐を単体試験。網羅率 80% 以上 |
| DB の決まり | 07 12章の13項目を、実際の PostgreSQL（Docker）で毎回試す |
| 権限 | 区分×API の全組合せ（13 4章） |
| E2E | 試作画面の業務の流れ①〜⑤と同じ流れを Playwright で |
| freee | 自動試験はにせもののアダプタで。試験用の事業所との結合試験は 15 の手順で手動＋記録 |

## 7. 開発環境の立ち上げ

```bash
pnpm install
docker compose up -d db            # PostgreSQL 16（ポート 5432）
pnpm --filter api prisma migrate deploy
pnpm --filter api prisma db seed   # spec/seed.sql の内容
pnpm dev                           # web: http://localhost:3000、api: http://localhost:4000
pnpm test                          # 単体・正解データ
```

`.env.example` に必要な設定の名前だけを書きます（値は書かない）。freee・SendGrid は、ローカルではにせものの adapters が既定です。
