## 1. 守るもの

| 守るもの | 重要度 | 理由 |
|---|---|---|
| freee の鍵（アクセストークン・リフレッシュトークン） | 最高 | 漏れると、許可の範囲で会計データを読み書きされる |
| 請求書・伝票（PDF・データ） | 高 | 取引の証拠。改ざんされると請求・税務に影響。電子帳簿保存法の保存の対象 |
| 受入れの記録（日報・便） | 高 | 請求の根拠 |
| お客さまの情報（会社名・住所・メールアドレス・サイン） | 高 | 個人情報（サインは個人を特定しうる）を含む |
| 利用者のパスワード | 高 | なりすましの防止 |
| 操作履歴 | 中 | 不正の調査・訂正の記録 |

## 2. 想定するおもな脅威と対策

| 脅威 | 対策 | 該当 |
|---|---|---|
| パスワードの総当たり・使い回し | 12文字以上、5回失敗で15分ロック、ログインは1分10回まで（IP ごと）、管理者は2段階の確認（メールのコード） | NFR-12、3章 |
| セッションの乗っ取り | Cookie は HttpOnly・Secure・SameSite=Lax、セッション ID は推測できない乱数（256ビット）、DB にはハッシュだけ保存、ログイン時に作り直す、無操作で自動ログアウト | NFR-13 |
| CSRF（ほかのサイトからの勝手な操作） | 更新系は `X-CSRF-Token` 必須、SameSite=Lax | 08 2章 |
| 権限を超えた操作（受付が請求・freee を操作） | すべての API で区分を確かめる（Guard）。受付・サイン端末の応答に金額を含めない | 4章、AC-13 |
| サイン端末からの不正な操作 | サイン端末の区分は `terminal` の API だけ。表示できる伝票は自分に送られたものだけ | FR-SGN-06 |
| SQL インジェクション | ORM・パラメータ付きのクエリだけを使う。文字列をつないだ SQL は書かない（レビューで確認） | 14 |
| XSS（画面への悪いスクリプトの埋め込み） | React の自動エスケープ、`dangerouslySetInnerHTML` を使わない、CSP（5章） | 5章 |
| ファイルのアップロードの悪用 | 紙伝票のスキャンは PDF だけ（先頭のバイトで確認）・20MB まで、ファイル名は保存に使わない（ID で保存）、画面には署名付き URL で返す | FR-SLP-11 |
| 請求書・伝票の改ざん | 送信後は DB のトリガーで変更・削除を禁止、PDF の SHA-256 を記録、Cloud Storage の保持ポリシー | 07 5章、02 6.3 |
| 操作履歴の消去 | 追記だけ（トリガーと DB の権限で UPDATE・DELETE を禁止） | 07 5章 |
| freee の鍵の漏えい | KMS で暗号化して DB に保存、画面・ログ・操作履歴に出さない、復号はジョブの中だけ、鍵の版を定期的に新しくする | 6章 |
| freee の連携の横取り（認可コードの盗用） | state（使い捨て・10分）を確かめる、リダイレクト先は固定、PKCE は freee の対応を確認できたら使う（Q-38） | 09 3章 |
| 外部からの偽の呼び出し（Webhook・ジョブ） | SendGrid の署名（ECDSA）、Cloud Scheduler の OIDC トークン（送り先と発行者）を確かめる | 08 2章 |
| 依存しているライブラリの脆弱性 | Dependabot・`pnpm audit` を毎週、重大なものは保守で更新 | 14 |
| 開発者・保守担当の誤操作・不正 | 本番の変更は GitHub Actions だけ、本番 DB への直接の接続は緊急時だけ（17 5章の手順・記録）、個人に本番の変更権限を付けない | 12 2.3 |
| サービス停止（大量アクセス） | Firebase Hosting・Cloud Run の自動の守り、ログインの回数制限、Cloud Run の最大インスタンス | ― |

## 3. 認証

| 項目 | 決まり |
|---|---|
| パスワードの保存 | argon2id（メモリ 19MB、反復 2、並列 1。OWASP の推奨値）。平文・元に戻せる暗号は使わない |
| パスワードの決まり | 12文字以上、よく使われるパスワードの一覧（上位1万件）に入るものは使えない。定期的な変更は求めない |
| 初回 | 管理者が作った仮のパスワードでログインし、すぐに変える（`must_change_password`） |
| ロック | 5回続けて失敗したら15分ロック。管理者がパスワードを初期化すると解除 |
| 2段階の確認 | 管理者は、ログインのあとにメールで届く6桁のコード（10分有効、5回まで）。freee の連携・登録・利用者管理ができる区分のため |
| サイン端末 | 端末用の利用者でログインしたまま使う（12時間で自動ログアウト）。端末を紛失したら管理者が無効にする |
| セッション | 受付・サイン端末：操作がなくても12時間、本社・管理者：無操作60分でログアウト。ログアウトで DB のセッションを無効にする |

## 4. 権限

利用者区分ごとの権限は 02 要件定義書 3.2 と 04 基本設計書 4章、API ごとの区分は openapi.yaml の `x-roles` です。試験では、区分×API の全組合せについて、許されない呼び出しが 403 になることを自動で確かめます（15 テスト計画書）。

## 5. 通信と画面の守り

| 項目 | 値 |
|---|---|
| TLS | 1.2 以上（Firebase Hosting・Cloud Run の既定） |
| HSTS | `Strict-Transport-Security: max-age=31536000; includeSubDomains` |
| CSP | `default-src 'self'; img-src 'self' data: blob: https://storage.googleapis.com; frame-ancestors 'none'; base-uri 'self'; form-action 'self' https://accounts.secure.freee.co.jp` |
| そのほかのヘッダ | `X-Content-Type-Options: nosniff`、`Referrer-Policy: same-origin`、`Permissions-Policy: camera=(), microphone=(), geolocation=()` |
| CORS | 同じドメインだけ（ほかのドメインからの API 呼び出しは許さない） |
| ファイル | 署名付き URL（5分で失効）。`Content-Disposition: inline; filename*=UTF-8''…` |

## 6. 秘密の情報の扱い

| 情報 | 保管 | 使い方 |
|---|---|---|
| freee のクライアント ID・シークレット | Secret Manager | API の起動時に読む |
| freee のアクセストークン・リフレッシュトークン | DB（`freee_connection`）に KMS で暗号化した値 | 使うときだけ復号し、メモリから早く消す。ログに出さない（ログの出力で `token`・`secret`・`password`・`authorization` の項目を伏せる） |
| SendGrid の API キー・Webhook の公開鍵 | Secret Manager | |
| セッションの署名鍵 | Secret Manager | 年1回変える（変えると全員ログアウト） |
| DB の接続 | IAM 認証（パスワードを持たない）。できない場合だけ Secret Manager のパスワード | |

開発者の PC・GitHub には、本番の秘密の情報を置きません（`.env` は Git に入れない。検証・本番の値は Secret Manager だけ）。

## 7. 個人情報の扱い

| 項目 | 決まり |
|---|---|
| 対象 | 請求先の担当者名・メールアドレス、伝票のサイン（運転手の手書き）、利用者の名前・メール |
| 目的 | 伝票の発行と受領の記録、請求書の送付だけに使う |
| 保存 | 02 6.2 の期間。期間を過ぎたものの扱いは保守で相談 |
| 開発・試験 | 試験には本番のデータを使わない。移行リハーサルで使う場合は、検証の環境に入れて終わったら消す |
| 委託先 | Google Cloud（データの保管）、SendGrid（メールの送信）、freee（会計） |

## 8. 記録と監視

- 操作履歴（`audit_logs`）：08 API設計書 5章の操作をすべて。7年以上保存。
- ログイン・ログイン失敗・ロック・パスワードの初期化・権限の変更も操作履歴に残します。
- アクセスのログ（Cloud Logging）：リクエスト ID・利用者 ID・IP・処理時間・ステータス。本文と秘密の情報は残しません。
- 1時間にログインの失敗が20回を超えたら、保守担当にメールで知らせます。

## 10. 事故が起きたとき

| 事象 | 最初の対応 |
|---|---|
| freee の鍵が漏れた疑い | SoilFlow で連携を解除（鍵を消す）→ freee の画面で連携を解除 → 原因の調査 → 再連携 |
| 利用者のパスワードが漏れた疑い | 管理者がその利用者を無効にし、パスワードを初期化 |
| 不正な操作の疑い | 操作履歴とアクセスのログで調べる。保守担当がフジモト様に報告 |
| 個人情報の漏えい | フジモト様と協議し、法令に従って報告・通知 |

詳しい手順は「17 運用・保守手順書」5章です。
